## 1. Context & Problem Statement

Prior to Critical Security Hotfix Sprint 0, order checkout tokens were generated insecurely in `engine/payment_gateway.py` line 77:
```python
"unlock_token": f"tok_{abs(hash(order_id)) % 1000000}"
```
This legacy scheme presents several significant vulnerabilities:
1. **Predictability**: The token is derived directly from the order timestamp (`ord_{int(time.time()*1000)}`) modulo 1,000,000, creating an address space of only 10^6 possible tokens that can be brute-forced in seconds.
2. **Ephemeral / Memory-Only State**: Tokens generated by checkout were appended to an in-memory list `self.orders` without backing database or cryptographic signatures. Upon server restart, all legacy tokens vanished from server memory.
3. **No Server-Side Verification**: Legacy tokens were never verified by the backend when users accessed `/api/leads/generate` or `/api/content/generate`, as entitlement checks were purely executed client-side in browser JavaScript.

With the deployment of the centralized server-side entitlement engine (`engine/security_guard.py`) utilizing cryptographically secure entitlement tokens (`ent_{sha256(order_id + timestamp)}`), a reconciliation strategy is required to transition legitimate historical customers to cryptographic tokens without service interruption.

## 2. Safety Guidelines for Legacy Token Migration

> [!CAUTION]
> **STRICT NON-DESTRUCTIVE RULES**:
> 1. Do NOT delete or invalidate historical order records in `appointments.json`, `leads_vault.json`, or payment logs.
> 2. Do NOT break access for any customer who completed a valid transaction.
> 3. Do NOT log customer emails or raw credit card / checkout information in plaintext.

## 3. Reconciliation Architecture & Phased Strategy

```mermaid
graph TD
    A["Customer Presenting Token"] --> B{"Token Format"}
    B -->|ent_... (Cryptographic)| C["Verify in active_entitlements.json"]
    C -->|Valid & Active| D["Grant Access (HTTP 200)"]
    B -->|tok_... (Legacy)| E["Legacy Reconciliation Gateway"]
    E --> F{"Order Exists in Historical Orders?"}
    F -->|Yes: Legitimate Order| G["Issue Cryptographic ent_ Token & Backfill"]
    G --> D
    F -->|No: Unverified / Guess| H["Reject Access (HTTP 403)"]
```

### Phase 1: Read-Only Audit & Order Log Extraction (Read-Only)
1. Inspect any existing order logs or session records in `storage/` and payment provider dashboards.
2. Extract historical order IDs, customer email hashes, and transaction timestamps.
3. Map any existing `tok_...` tokens to verified Lemon Squeezy or checkout order IDs.

### Phase 2: Dual-Token Verification Window (Backward Compatibility)
1. During a 30-day grace period, when a user presents an `Authorization: Bearer tok_...` header:
   * The security engine inspects a legacy reconciliation mapping (`storage/legacy_token_map.json`).
   * If the `tok_...` corresponds to a verified historical purchase, the system automatically mints a modern `ent_...` cryptographic token.
   * The response returns a transition header: `X-Migrated-Entitlement-Token: ent_...`.
   * Client-side JavaScript updates `localStorage.setItem("leakgrader_token", new_token)`.
2. Unverified `tok_...` tokens (brute-forced or forged) are rejected with `HTTP 403 {"error": "entitlement_required", "details": "unrecognized_token"}`.

### Phase 3: Webhook Backfill
For customers with active Lemon Squeezy subscriptions whose tokens were lost during server restarts:
1. Trigger a read-only subscription reconciliation job against the Lemon Squeezy API (`/v1/subscriptions`).
2. For each active subscription in status `active` or `on_trial`, generate an entry in `storage/active_entitlements.json` tied to the customer email hash.
3. When the customer logs in or contacts support, their entitlement is instantly recognized.

### Phase 4: Full Deprecation of Insecure Tokens
1. At the conclusion of the 30-day migration window, disable support for `tok_...` patterns completely.
2. Ensure that all tokens in circulation adhere to the 256-bit cryptographic standard.

## 4. Verification & Testing Protocol

Before enabling the legacy migration in production, the following test cases must be verified locally in staging:
1. **Verified Legacy Order Test**: A mock historical order with legacy token `tok_123456` mapped in `legacy_token_map.json` is successfully upgraded to an `ent_` token upon first API call.
2. **Forged Legacy Token Test**: An arbitrary `tok_999999` not in the verified map is rejected with HTTP 403.
3. **Double Upgrade Test**: Multiple requests with the same legacy token return the same consistent `ent_` token without creating duplicate entitlement entries.
